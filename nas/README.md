# WhoGa NAS 2.5.4 · 직접 실행한 Chromium으로 수집

**새 코드로 시작하면 브라우저 준비 후 전체 수집을 최초 1회 자동 실행합니다.** [2.5.3 동작과 원격 업데이트](../docs/NAS-2.5.3-FIRST-START.md)를 확인하세요.

[2.5.2 업로드 안내 개선 및 업데이트 절차](../docs/NAS-2.5.2-UPLOAD.md)를 확인하세요.

2026-10-26 사용자 NAS에서 122카드·578개별매물 `full-passed`를 확인했습니다. [성공 환경과 교훈](../docs/NAS-COLLECTION-LESSONS.md)에 실행 조건·수정 원인·재현 순서·검증 범위를 기록했습니다. 아래 2.5·2.4 설명은 이전 버전의 이력입니다.

**2.5.4 주소 입력:** 긴 fin.land 지도 주소와 new.land 단지 주소를 붙여넣고 입력란 밖을 누르면 `https://fin.land.naver.com/complexes/번호`로 변환합니다. 설정을 저장한 뒤 실행하세요. 변환은 선택한 단지의 매매 수집용이며 원래 면적·거래유형·개별 매물 선택은 가져오지 않습니다.

DS420+ / 메모리 6GB / Container Manager용입니다. 기존 관리 화면에 로그인한 뒤 **브라우저 화면 열기**를 누르면 실제 Chrome 창을 보고 조작할 수 있습니다.

- 관리 화면: `http://NAS주소:8899`
- 브라우저 화면: `http://NAS주소:8899/desktop/` — 같은 관리자 로그인 사용
- 원문 열기·표본 검사·전체 수집이 모두 같은 창을 사용합니다. 작업 후에도 창을 남깁니다.
- 화면 접속을 닫아도 NAS의 브라우저·예약 수집은 계속 동작합니다.
- 기존 감시 설정·주기 실행·검증 결과·GitHub 업로드 기능을 유지합니다.

## 기존 설치 업데이트

1. 기존 컨테이너에서 실행 중인 수집을 중지합니다.
2. ZIP 안의 `whoga/nas/`와 `whoga/experiments/`를 기존 WhoGa 폴더에 덮어씁니다.
3. 기존 `.env`, `nas-config`, `collector-runs`는 유지합니다. 이 ZIP에는 비밀번호나 토큰이 포함되지 않습니다.
4. Container Manager에서 **기존 프로젝트**를 다시 빌드·시작합니다. 프로젝트 이름과 볼륨을 그대로 유지해야 기존 설정을 읽습니다.
5. 기존 관리자 계정으로 8899에 로그인합니다. **브라우저 화면 열기 → 브라우저 확인 → 원문 열기** 순서로 확인합니다.
6. 관리 화면 하단의 **버전 2.5.1 · 커밋 · 코드 해시**를 확인합니다. ZIP의 `VERIFICATION.json`에 적힌 `sourceCommit`·`sourceFingerprint`와 같아야 합니다. 파일만 덮어쓰고 기존 이미지를 재시작하면 새 코드가 적용되지 않으므로 반드시 다시 빌드합니다.

Compose를 사용한다면 기존 설치 방식과 같은 파일을 선택합니다. 폴더 예시는 기존 설치 위치에 맞게 바꿉니다.

```sh
cd /volume2/docker/whoga/nas
# Container Manager / named volume 방식
sudo docker compose -f compose.yaml up -d --build
# 기존 .env + nas-config 폴더 연결 방식이었다면 위 명령 대신:
sudo docker compose -f compose.bind.yaml up -d --build
```

업데이트 중 `down -v`를 실행하거나 기존 설정 볼륨을 삭제하지 마세요. `compose.yaml`은 기존 named volume 이름을, `compose.bind.yaml`은 기존 폴더·UID·비밀번호 설정을 유지합니다.

## 처음 설치

ZIP의 `whoga` 폴더를 NAS의 Docker 작업 폴더에 둡니다. Container Manager에서 `whoga/nas`를 프로젝트 경로로 선택하고 `compose.yaml`을 빌드·시작합니다.

첫 관리자 계정은 `admin`이며, 최초 비밀번호는 컨테이너 로그에 한 번 표시되고 설정 볼륨에 보관됩니다. 기존 설치의 비밀번호는 변경하지 않습니다.

폴더 연결 방식을 선호한다면 일반 NAS 계정으로 `nas/setup.sh`를 실행합니다. Docker 접근 권한이 필요하면 위의 Docker 명령에만 관리자 권한을 적용합니다.

## 2.5에서 적용한 NAS 실측 결과

사용자 NAS의 2.4 보고서에서 직접 실행한 Chromium의 PC·400px·Android 조건은 모두 `매물122개도움말 보기` 제목과 초기 카드 30개를 표시했습니다. Playwright가 브라우저까지 실행한 조건은 오류 화면으로 이동했습니다. 같은 버전·메모리 한도에서 차이가 관측됐으므로, 기본 수집 브라우저를 성공한 **직접 실행 + CDP 연결 + PC 1440×900**으로 바꿨습니다. Playwright는 기존 창의 조작과 추출에 사용합니다. 특정 실행 옵션 하나가 원인이라고 단정하지 않습니다.

2.4의 비교 판정은 제목 끝의 `도움말 보기` 문구 때문에 표시된 목록을 놓쳤습니다. 2.5는 목록 제목 앞부분의 수량을 읽으며 상단 `매매122`로 대체하지 않습니다. 매물 탭·매매 필터가 포함된 주소로 접속하고, 이미 매매인 필터를 다시 누르지 않습니다. 표본 검사 후에는 단지 번호를 확인해 같은 지도 탭의 로딩과 세션을 유지합니다. 초기 `매물0`은 최대 45초 기다리되 실제 0건과 불완전한 수집은 저장하지 않습니다.

업데이트 후 **원문 열기 → 표본 검사 → 전체 수집** 순서로 진행합니다. 비교 시험을 다시 할 필요는 없습니다. `probe-passed`는 표본 추출·정규화 성공, `full-passed`는 전체 카드 및 묶음 매물 검증 성공입니다. 실패하면 **진단 JSON 저장**에 정확한 단계와 오류가 남습니다. 실제 NAS의 122개 전체 JSON 생성은 이 버전으로 실행해 확인해야 하며, 초기 30개 표시 증거를 전체 수집 완료로 표시하지 않습니다.

기본 브라우저는 새 창을 시작할 때마다 별도 임시 프로필을 사용합니다. 실행 중에는 원문 열기·표본 검사·전체 수집이 같은 창과 세션을 공유합니다. 비교 시험이나 컨테이너 재시작 후에는 이전 탭이 누적되지 않도록 새 프로필의 탭 하나로 복구합니다. NAS의 관리자 계정·GitHub 토큰·예약 설정 볼륨은 유지됩니다. 브라우저 준비가 끝난 뒤 수집을 연결하고, 비교 종료 후에도 기본 브라우저 준비를 확인해 연결합니다.

## 실제 원문 시험

접속 실패가 계속되면 **접속 환경 비교**를 한 번 실행합니다. 약 10분 동안 기존 창을 닫고 같은 Chromium을 하나씩 실행합니다. 비교가 끝나거나 중지되면 기존 임시 프로필로 기본 브라우저가 다시 열립니다. 기존 탭의 화면은 초기화되므로 작업 중인 탭이 없는 상태에서 실행합니다.

| 실행 방식 | 화면 조건 |
| --- | --- |
| Playwright가 Chromium 실행 | PC 1440×900 / PC UA를 유지한 400×848 / Android 모사 400×848 |
| Chromium 직접 실행 후 CDP 연결 | 동일한 세 화면 조건 |

각 조건은 로그인·쿠키가 없는 새 임시 프로필을 사용합니다. 같은 브라우저 버전·한국어·서울 시간대·DPR 1을 사용하고, 모바일 모사는 UA·Client Hints·터치·화면 설정을 함께 바꿉니다. 화면 크기만 줄인 조건과 모바일 UA 조건을 구분합니다. Android 모사는 Linux Chromium에서 실행되며 실제 Android OS나 저사양 브라우저로 바뀌는 것은 아닙니다.

대상은 저장된 단지 주소에 `?tab=article&articleTradeTypes=A1`을 붙인 PC 비교 주소입니다. 조건마다 최초 접속과 한 번의 새로고침을 비교하고 각각 최대 45초 동안 목록을 관찰합니다(문서 연결 제한 별도 30초). 이미 404 안내 페이지로 이동했다면 원래 주소에 다시 접속합니다. 접근 확인 화면이 나타나면 비교를 중단합니다. `/dev/shm` 설정, 메모리 상한, 인증서 검증, 사이트 CSP는 유지합니다.

**최근 실행 진단**에서 조건별 결과를 plain text로 확인하고 **진단 JSON 저장**으로 전체 보고서를 내려받습니다. 같은 실행 폴더에 조건별 스크린샷 12장, 실제 UA·화면·터치·브라우저 실행 옵션 일부, 매물 제목과 처음 최대 3개 카드의 표시 텍스트, `list`·`mount` 등 응답, 메모리·임시 공간 사용량을 저장합니다. JSON의 `screenshot` 파일명은 진단 다운로드 주소 마지막 `diagnostics.json`을 해당 이름으로 바꾸어 같은 인증으로 볼 수 있습니다. 요청 본문·쿠키·인증 헤더는 수집하지 않습니다.

`비교 기록 완료`는 시험 종료이며 목록 성공 여부는 조건별로 별도 표시합니다. 목록 제목의 수량과 카드/매물 링크가 함께 있어야 `목록 표시`로 판정합니다. 모바일 화면 표시 성공을 기존 데스크톱 수집기의 전체 검증 성공으로 대체하지 않으며, 비교 결과는 자동 업로드하지 않습니다. 메모리는 접속 전후의 실제 값입니다. 작은 화면이 반드시 적은 메모리를 사용한다고 가정하지 않습니다.

ChatGPT 클라우드 브라우저의 버전·실행 옵션·IP·프로필을 이 도구에서 조회할 수 없으므로 동일한 환경 복제는 검증하지 않았습니다. GitHub Actions와 NAS 비교는 같은 Docker 이미지와 비교 코드를 사용하지만 IP·호스트 커널·CPU·네트워크는 다릅니다. `nas-desktop.yml`의 수동 실행에서 `live_comparison`을 켜면 실제 네이버 비교 보고서가 Actions artifact에 저장됩니다. 기본 자동 검사는 외부 접속 없는 로컬 fixture입니다.

Selenium은 WebDriver로 브라우저를 조작하고, Puppeteer·Playwright는 Chromium 제어에 CDP 등을 사용합니다. 도구 교체만으로 같은 Chromium의 네트워크 오류나 자원 제한이 해결된다고 볼 수 없습니다. 먼저 직접 실행과 Playwright 실행을 비교하여 실행 옵션의 영향부터 확인합니다. Firefox는 다른 엔진의 비교 대상으로 사용할 수 있으나 이 버전의 NAS 수집기·CDP 진단에는 연결되지 않습니다.

1. 관리 화면에서 단지 주소를 저장합니다. 기본은 `https://fin.land.naver.com/complexes/140635`입니다.
2. **브라우저 화면 열기**를 눌러 창을 별도 탭에 띄웁니다.
3. 관리 화면에서 **원문 열기**를 누릅니다. `원문 탭 열림`은 문서 응답 확인이며 수집 성공을 뜻하지 않습니다.
4. 실제 지도·매물 패널을 확인합니다. 같은 문서가 로딩 중이면 탭을 유지하며 기다립니다.
5. **표본 검사**, 이어서 **전체 수집**을 실행합니다. 자동 수집 중에는 원격 화면 조작을 잠시 멈춥니다.

초기 문서 응답은 최대 3분, 매물 패널 표시는 최대 5분 기다립니다. 이미 열려 있는 같은 단지 탭은 초기화하지 않고 재사용합니다. 접근 제한·인증 화면은 자동으로 우회하지 않습니다.

휴대폰은 가로 화면이 보기 편합니다. 화면 맞춤이 기본이며, `보기만`을 선택하면 원격 입력을 막습니다. 화면이 끊기면 **다시 연결**을 누릅니다. 브라우저 창 자체를 닫으면 컨테이너가 데스크톱을 재시작할 수 있으므로 화면 확인 탭만 닫습니다.

## 데이터·GitHub 동작

현재 수집기의 카드/개별 매물 스키마와 `publicationEligible=false`를 유지합니다. 전체 수집 성공 때만 `nas-imports/단지번호/실행ID.json` 업로드가 가능합니다. **이 버전의 업로드는 검증 자료 전달이며 운영 호가앱의 `data/`·Pages 자동 갱신은 별도입니다.** 기존 GitHub 설정은 NAS에만 보존되고 브라우저 화면에 전달하지 않습니다.

결과·로그는 기존 `/output`, 계정·감시 설정은 기존 `/config` 볼륨에 보관합니다. 브라우저의 임시 프로필은 컨테이너 재시작 시 초기화됩니다. 재시작 전에 진행 중이던 작업은 성공으로 처리하지 않습니다.

## PC 없이 매일 수집·GitHub 자동 전송

`집 NAS의 Chrome → 전체 수집·검증 → NAS에 JSON 저장 → GitHub API로 파일·커밋 생성`

NAS가 직접 전송하므로 PC나 별도의 GitHub Actions 수집 작업이 필요하지 않습니다. NAS와 컨테이너는 켜 두어야 합니다.

1. `http://NAS주소:8899`에 로그인합니다.
2. **예약 수집 켜기 → 매일 지정 시각**을 선택하고 시간을 입력합니다. 기본은 **08:45, 한국 시각**입니다. 기존 설치는 이전 분 간격을 유지하므로 매일 지정 시각으로 직접 변경합니다.
3. **GitHub 업로드 설정**에서 저장소를 `PoeticEcho/whoga`, 기존 브랜치를 `map-collector-v2`로 지정합니다.
4. GitHub의 **Settings → Developer settings → Personal access tokens → Fine-grained tokens**에서 `PoeticEcho/whoga`만 선택하고 **Contents: Read and write** 권한으로 토큰을 만듭니다. 토큰은 NAS 설정 화면에만 입력합니다.
5. **전체 수집 성공 후 자동 업로드**를 켜고 **설정 저장**을 누릅니다. 이어 **저장된 설정으로 연결 확인**을 누릅니다. 이는 저장소·브랜치 접근 확인이며, 실제 쓰기는 첫 전체 수집 후 확인됩니다.
6. 화면에 표시된 **다음 실행**을 확인합니다. 매일 해당 시각부터 전체 수집하고, 검증을 통과하면 `nas-imports/140635/실행ID.json`에 업로드합니다. 완료 후 **업로드한 파일 보기**로 확인할 수 있습니다.

시각은 NAS나 접속 기기의 시간대 설정과 관계없이 `Asia/Seoul`로 계산합니다. 수동 브라우저 확인·원문 열기는 매일 예약 시각을 바꾸지 않습니다. 예약 실행 중에는 다른 수집·업로드를 겹쳐 실행하지 않습니다.

다음 실행과 당일 예약 실행 여부를 디스크에 저장합니다. 재시작해도 당일 실행을 반복하지 않으며, 전원이 꺼져 놓친 예약이 있으면 복구 후 한 번 실행하고 다음 날 예약으로 넘어갑니다. 과거 날짜를 여러 번 소급 수집하지 않습니다. 예약 수집이 실패하면 그날 자동 재시도는 하지 않고, **전체 수집**으로 수동 재시도할 수 있습니다.

검증 실패 시 GitHub에 업로드하지 않습니다. 업로드만 실패한 경우 JSON은 NAS에 남으며, 다음 수집 전에 **GitHub 업로드** 버튼으로 다시 전송할 수 있습니다. 운영 페이지의 `data/`·Pages 갱신은 이 검증 JSON을 운영 스키마로 연결하는 후속 단계입니다.

## DS420+ 실행 조건

- 6GB NAS에서 컨테이너 메모리 상한은 3GB, 공유 메모리는 512MB입니다. DSM·다른 패키지의 사용량도 리소스 모니터로 확인합니다.
- 기존 DS420+ 호환 설정을 유지합니다. CPU quota·PID 제한·사용자 지정 seccomp 설정을 추가하지 않았습니다.
- 컨테이너는 일반 사용자, 읽기 전용 루트, 권한 제거, `no-new-privileges` 설정으로 실행합니다. 업로드본의 Chromium 샌드박드 호환 설정을 유지합니다.
- 추가 공개 포트는 없습니다. VNC·WebSocket 변환기·CDP는 컨테이너 내부 loopback에서만 연결합니다. 외부 접속은 기존 8899의 관리자 인증을 사용합니다.
- 내부망을 기본으로 합니다. 외부 연결은 VPN 또는 DSM HTTPS 리버스 프록시를 사용하고 WebSocket 전달을 켭니다. 프록시가 원래 `Host`를 전달해야 합니다.

## 확인 범위

화면 연결·실제 원격 클릭·같은 Chrome 연결·수집 환경 검사·재시작 후 설정 유지는 Docker 통합 검사에서 확인합니다. 기본 테스트는 로컬 예제 화면을 사용하며 네이버에 접속하거나 GitHub에 자료를 쓰지 않습니다. 네이티브 브라우저에서 목록 추가 로딩, 묶음 펼치기, 표본 후 전체 수집, 단지 세션 보존, JSON 건수·매물번호 검증도 실행합니다. 수동 Actions의 `live_collect=probe/full`은 실제 사이트를 검사하지만 결과를 운영 데이터나 GitHub 수집 브랜치에 게시하지 않습니다.

**사용자 NAS의 커널·Container Manager에서의 실제 구동과 네이버 전체 수집 성공은 NAS 설치 후 확인해야 합니다.** GitHub 러너에서의 연결 실패가 NAS에서도 같은 결과라는 뜻은 아닙니다.

로그 확인:

```sh
sudo docker compose logs --tail 100 collector
```

최초 로그인 비밀번호가 포함된 로그와 `.env`, 설정 볼륨은 공개하지 않습니다.

## browse · smoke · probe 결과와 실패 진단

- `browse → page-opened`: 문서 HTTP 응답을 확인하고 작업을 끝냅니다. Chrome 창과 페이지의 로딩은 계속됩니다. 매물 목록 성공을 뜻하지 않습니다.
- `smoke → browser-ready`: 같은 보이는 Chromium에 연결하고 화면을 저장했다는 뜻입니다. 네이버 데이터를 검사하지 않습니다.
- `probe → probe-passed`: 단지 패널·매매 필터·단지번호·목록 건수·처음 최대 3개 카드와 묶음 매물을 확인합니다.

단계는 `probe:navigation → complex-panel → sale-filter → complex-identity → list-count → first-cards → extract-card → normalize`처럼 로그에 남습니다. 전체 수집에서는 스크롤·묶음 펼치기·수량 검증도 기록합니다.

기존 코드의 `매물 숫자 개` 제목 조건은 `매물 숫자`·`매물 숫자개` 모두 읽도록 수정했습니다. 단지 패널 안의 **매물 목록 제목**만 사용하며 상단 `매매 숫자`로 대신하지 않습니다. 0건·필수 항목 누락·부분 수집은 계속 실패로 처리합니다. 모바일 에뮬레이션을 사용했다면 데스크톱 수집 화면과 다를 수 있으며, 진단에 실제 뷰포트·UA·모바일 여부가 표시됩니다.

작업이 끝나면 **최근 실행 진단 → 진단 JSON 저장 / 실행 화면 보기**에서 확인할 수 있습니다. 저장 위치는 같은 실행 폴더 `/output/jobs/작업ID/runs/runId/`입니다.

- `status.json`: 구체적인 실패 단계, 최종 URL, 제목, 오류 원문, 브라우저·빌드 버전.
- `diagnostics.json`: 단계 이력, 실제 화면의 제목·목록 카드 수·거래 필터, 환경, CSP·네트워크·JavaScript 오류.
- `probe-list-count.png` 등: 마지막 단계의 스크린샷. 실패 시에도 별도로 저장을 시도합니다.

`assessment`는 접근·인증 확인 화면, 오류 화면, 카드 표시, 로딩/빈 목록, 모바일 화면 등을 구분한 진단입니다. 카드가 보인다는 판정만으로 전체 수집 성공으로 처리하지 않습니다.

`duringRun`은 이번 작업 중 관측한 오류이고, `browserHistory`는 원문 열기 이후 브라우저가 별도로 기록한 최근 이력입니다. **이력에 있던 CSP 오류를 이번 probe의 확정 원인으로 간주하지 않습니다.** 문서 응답의 CSP 헤더·HTML meta 정책, Chrome의 `blockedReason=csp`·위반 directive, JS 예외를 함께 확인합니다. 쿠키·인증 헤더·API 응답 본문은 기록하지 않으며 진단 파일은 자동 GitHub 업로드 대상에 포함되지 않습니다.

한국어·서울 시간대·화면 표시 여부와 사이트 스크립트 정책은 각각 다른 조건입니다. 실제 접속 IP는 NAS의 인터넷 경로를 따르고, 보이는 Chromium도 사이트의 CSP를 그대로 적용합니다. CSP 오류만으로 자동화 탐지를 확정할 수 없습니다. 이번 사용자 로그의 제목 대기 시간 초과 역시 네트워크 오류인지 제목 조건 문제인지 추가 진단이 필요합니다.

ZIP에는 원본 Git 커밋 정보가 포함되며, NAS에서 빌드할 때 런타임 소스의 SHA-256을 계산해 이미지에 넣습니다. 버전·커밋·해시가 관리 화면과 각 실행 결과에 함께 기록되어 NAS/GitHub 코드 일치 여부를 확인할 수 있습니다.

## ERR_INSUFFICIENT_RESOURCES 확인

이 오류는 Chromium이 자원 또는 내부 요청 한도 문제로 요청을 완료하지 못했다는 뜻입니다. 실제 RAM 부족·공유 메모리·임시 공간·파일 디스크립터·동시 요청 한도 등을 구분해야 하며, 이 문구만으로 NAS의 6GB 메모리가 부족하다고 단정하지 않습니다. HTTP 401·500, Quirks Mode·이미지 크기 경고와도 별개의 증거입니다.

2.4은 Playwright의 `--disable-dev-shm-usage` 기본 옵션을 제외해 컨테이너의 독립 `/dev/shm`을 사용하도록 설정합니다. `/tmp`의 임시 프로필·캐시와 공유 메모리가 한 512MB 공간에 몰리는 것을 줄이려는 변경이며, 이번 NAS 오류의 원인으로 확정한 것은 아닙니다. 컨테이너 메모리 상한 3GB, `/tmp` 512MB, `/dev/shm` 512MB 설정을 사용합니다. 각 tmpfs의 상한은 미리 전부 예약되는 RAM 용량이 아니며, 사용량은 컨테이너 메모리 한도에 포함됩니다.

최근 실행 진단에 컨테이너 메모리 사용량·한도, `/tmp`·`/dev/shm` 여유 공간과 실제 브라우저의 우회 옵션 여부를 표시합니다. JSON의 `resources`에는 cgroup v1/v2 수치, 누적 OOM/한도 도달 지표(지원되는 경우), NAS 전체 가용 메모리, 파일 디스크립터 한도·브라우저 프로세스 수 등도 저장합니다. 전체 프로세스 실행 인수는 저장하지 않습니다. 누적 지표가 있다는 이유만으로 이번 실행의 실패 원인으로 단정하지 않습니다.

시험은 실행 중인 수집을 중지하고 컨테이너를 다시 시작한 뒤, NAS Chrome 탭 한 개에서 원래 대상 주소를 여는 순서로 진행합니다. 오류 안내 페이지 자체를 새로고침하는 것과 구분합니다. 문제가 나타난 뒤 **브라우저 확인 → 진단 JSON 저장**으로 사용량과 최근 브라우저 이력을 확인합니다. `duringRun`에 없던 자원 오류도 `browserHistory`에 남을 수 있습니다.

Docker 통합 검사는 실제 메모리 한도·공유 메모리 크기와 headed Chromium의 실행 옵션을 확인합니다. 실제 Naver 홈페이지의 자원 오류나 단지 요청의 401 해결 여부는 사용자 NAS에서 별도로 확인해야 합니다.
