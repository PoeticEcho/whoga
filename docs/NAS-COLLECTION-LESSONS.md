# WhoGa NAS 수집 성공 환경과 재현 절차

2026-10-26 한국 시각, 사용자 NAS에서 **2.5.1 전체 수집·검증이 성공했다.** 화면의 122카드를 모두 읽고, 묶음 안의 개별 매물을 포함해 578개를 검증했다. 이 문서는 같은 환경을 재현하고 다음 문제를 증거로 판단하기 위한 기록이다.

## 1. 어디까지 확인됐는가

| 단계 | 확인 결과 | 근거 |
| --- | --- | --- |
| 원문 접속·목록 표시 | 성공 | 사용자 NAS 화면 및 진단 |
| 표본 수집·정규화 | 성공 | 3카드 / 47개별매물 |
| 전체 추가 로딩 | 성공 | 30 → 60 → 90 → 120 → 122카드 |
| 전체 추출·검증·NAS JSON 저장 | 실행 로그상 성공 | `status=full-passed`, `full.cards=122`, `full.articles=578` |
| GitHub 전달 | 이 성공 로그만으로는 미확인 | NAS 업로드 상태와 저장소의 실제 새 JSON을 별도 대조해야 함 |
| 운영 앱·Pages 반영 | 이번 수집 성공에 포함되지 않음 | `publicationEligible=false`, `nas-imports/`는 검증 자료 전달 경로 |

성공 실행은 `48554cc571f94d679f6018fc3781dac2`, 07:40:59 시작, 07:45:20 완료(4분 21초)다. 파일 내용 자체를 이 기록에 첨부한 것은 아니며, 사용자가 제공한 진단·실행 로그를 근거로 한다. 공개 가능한 최소 증거는 [검증 요약 JSON](verification/nas-2.5.1-2026-10-26.json)에 보관한다. 원문 전체·관리자 인증·토큰·개인 접속 주소는 넣지 않는다.

122와 578은 해당 시점 관측치다. 다음 실행의 정답으로 고정하지 않는다. 카드 수는 화면의 묶음 단위이고, 개별 매물 수는 묶음 구성원을 포함하므로 두 숫자가 다르는 것이 정상이다.

실행 경로는 `nas/desktop.py` → `nas/browser_runtime.py` → `nas/run.py` → `experiments/supplied-v2/collector.py`다. 관리 화면과 보이는 브라우저는 기존 8899 포트의 인증을 공유하고, CDP는 외부 공개하지 않는다.

기존 NAS 호환 실행 인수에 `--no-sandbox`가 포함되어 있다. 이것을 새 해결책이나 단독 성공 원인으로 해석하지 않는다. 컨테이너는 일반 사용자·읽기 전용 루트·capability 제거·`no-new-privileges`를 사용한다. 실제 인수와 자원 설정은 코드 및 Compose 파일을 함께 확인한다.

## 3. 어떤 과정을 거쳐 해결했는가

1. **접속 도구가 다르면 결과도 달랐다.** 기존 클라우드 브라우저 성공 이력과 Firecrawl/Actions 실패 이력이 있었다. 같은 주소라도 실행 환경·IP·브라우저 버전·프로필·로딩 상태가 달라 NAS와 결과가 같다고 가정할 수 없었다. 과거 이력은 해당 실행의 증거로 한정한다.
2. **NAS 2.4 비교 기록을 바탕으로 브라우저 시작 방식을 조정했다.** 이전 배포 문서에는 직접 시작한 Chromium의 목록 표시 성공과 Playwright가 시작한 조건의 실패가 기록되어 있다. 2.5는 직접 시작 + CDP 연결을 기본으로 삼았다. 옵션 하나가 유일한 원인이라는 통제 실험 결론은 아니다.
3. **보이는 목록을 코드가 잘못 판정할 수 있었다.** `매물122개도움말 보기` 같은 실제 제목을 기존 조건이 놓쳤다. 2.5는 단지 패널의 목록 제목 앞부분에서 수량을 읽게 했다. 상단 요약 `매매122`로 검증을 대신하지 않는다.
4. **2.5에서 원문·표본은 성공했지만 전체 버튼은 사전검사에서 멈췄다.** 실패 실행 `16fb0b7395e544ec935306e59ad61249`는 `probe:complex-identity`에서 매물 탭의 접근성 이름을 찾다가 30초 시간 초과가 났다. 당시 DOM에는 카드 30개가 있었다. 전체 스크롤 실패라고 결론 내릴 근거가 아니었다.
5. **수동 스크롤 성공이 문제 범위를 좁혔다.** 사용자가 NAS의 같은 브라우저에서 끝까지 볼 수 있었다. 이는 목록을 추가 표시할 수 있다는 증거지만, 묶음 추출·정규화 성공까지 증명하지는 않았다.
6. **2.5.1은 단지 확인을 DOM 링크 기준으로 수정했다.** `#complex_detail` 안의 매물 탭 링크에서 단지번호를 읽고 요청 번호와 대조한다. 숨김 탭·동일 단지 중복 탭을 허용하되 다른 번호·충돌·누락은 중단한다. 검증을 삭제하거나 30초 제한만 늘리지 않았다.
7. **로컬 재현과 실제 NAS 검증을 각각 확인했다.** 합성 Chromium 예제에서 기존 탭 탐색 시간 초과와 수정 후 122카드 전체 처리를 검증했고, 이어 사용자 NAS에서 실제 122카드/578개별매물 `full-passed`를 확인했다. 새 NAS 진단의 매물 탭에는 `ariaHidden=true`가 관측됐다. 이는 기존 접근성 탐색이 취약했던 화면 조건을 뒷받침한다. 이전 실패 순간의 DOM까지 소급 확인한 것은 아니다.

## 4. 재현 순서와 성공 기준

1. 기존 프로젝트·설정·결과 볼륨을 유지한다. 설치 방식에 맞는 `nas/compose.yaml` 또는 `nas/compose.bind.yaml`을 사용해 **다시 빌드**한다. 단순 컨테이너 재시작과 구분한다.
2. 관리 화면에서 버전과 코드 해시를 확인한다. Git에서 직접 빌드한다면 `VCS_REF`에 실제 HEAD를 전달하면 커밋도 결과에 기록된다. 배포 ZIP의 `sourceCommit=null`은 실패 신호가 아니며 원본 기준은 `baseSourceCommit`이다.
3. 보이는 브라우저를 열고 **원문 열기 → 표본 검사 → 전체 수집** 순서로 진행한다. 자동 작업 중에는 수동 스크롤·필터 변경을 멈춘다.
4. 전체 버튼은 사전 표본검사를 다시 수행한다. `probe:*` 뒤 `full:complex-identity-verified`, 추가 로딩, 전체 카드·묶음 추출, `full:verify-counts`, `full:normalize` 순으로 진행한다.
5. 최종 `status=full-passed`, 표시 카드 수=수집 카드 수, 매물번호·가격·묶음 수량 검증 통과를 확인한다. `phase=full:normalize`는 마지막 단계명이며 실패 상태가 아니다.
6. NAS 결과는 `/output/jobs/<jobId>/runs/<runId>/full.json`에 저장된다. `diagnostics.json`과 최종 `status.json`을 함께 확인한다.
7. GitHub 자동 업로드를 켰다면 설정된 브랜치의 `nas-imports/140635/<runId>.json`과 실제 추가 커밋을 확인한다. 단순 연결 확인은 쓰기 성공을 증명하지 않는다.

GitHub 결과는 `mode=full`, 단지번호·매매 필터, 이번 `runId`·`collectedAt`, 카드 배열 길이·표시 수량 일치, 개별 매물 배열 길이·중복없는 번호, 카드의 `articleNos` 참조가 맞아야 한다. 기존 07:45 성공 자료를 08:00 새 실행의 성공으로 재사용하지 않는다.

2026-10-26 08:00 시험은 NAS 예약과 GitHub 수신 확인을 구분한다. 이 대화의 클라우드 환경에는 NAS 접속 주소·인증·VPN 경로가 없어 NAS 예약을 직접 설정하지 못했고 사용자에게 설정 확인을 요청했다. ChatGPT의 08:00 확인 작업은 GitHub 수신을 확인할 뿐 NAS 수집을 실행하지 않는다. 시험 때문에 매일 예약 시각을 바꿨다면 시험 후 원래 시각으로 되돌린다. 미래 시험 결과는 실제 증거가 생긴 뒤 별도로 기록한다.

## 5. 다음에도 지킬 교훈

- **마지막 실패 단계부터 읽는다.** ‘전체 버튼 실패’를 ‘전체 스크롤 실패’로 바꾸어 해석하지 않는다.
- **접속·표시·추출·검증·저장·전송·배포를 나눈다.** HTTP 200, 화면 122개, `full-passed`, GitHub 파일 생성은 서로 다른 증거다.
- **같은 화면 상태에서 재현한다.** 초기 화면만 테스트하면 표본검사 후 숨겨지는 탭을 놓친다. 표본→전체 순서와 동일 세션 유지가 회귀 시험에 포함돼야 한다.
- **식별은 안정적인 구조로, 수량은 실제 목록으로 검증한다.** 접근성 이름·sticky 헤더 표시 상태에 단지번호 확인을 종속시키지 않는다. 요청 URL을 그대로 믿어 검증을 생략하지 않는다.
- **원인을 확인한 부분만 수정한다.** 이번 2.5.1의 핵심은 단지 탭 확인이다. 스크롤 전체 재작성, 성공 판정 완화, 도구 전면 교체는 필요하지 않았다.
- **자원 오류는 수치와 실행 시점을 함께 본다.** 과거 브라우저 이력의 실패를 이번 실행 원인으로 옮기지 않는다. 이번 성공에서는 실행 중 CSP·자원·JavaScript 오류가 관측되지 않았다.
- **검증된 환경을 고정하고 변경 이유를 남긴다.** NAS 모델만 적지 말고 브라우저·라이브러리·실행 방식·화면·언어·세션·메모리·코드 해시까지 남긴다. 다른 클라우드의 성공·실패를 그대로 일반화하지 않는다.
- **부분 자료로 정상 결과를 덮어쓰지 않는다.** 카드·묶음 수량, 가격, 매물번호 검증을 통과해야 저장·업로드 성공으로 판단한다. 접근 확인 화면에서는 중단한다.
- **진단과 비밀정보를 분리한다.** 다음 장애를 확인할 탭 링크·숨김 상태·스크롤 위치는 남기되, 쿠키·인증 헤더·토큰·전체 요청 본문은 남기지 않는다.

## 6. 회귀 검사

```sh
python -m unittest discover -s nas -p 'test_*.py'
python nas/check_collection_regression.py --chromium /usr/bin/chromium
```

기존 단위 검사 40개와 브라우저 회귀 검사 5개가 통과했다. 로컬 브라우저 검사는 Chromium 154.0.8037.57 / Playwright 1.62.0 / headless 합성 예제이므로 사용자 NAS 153/1.63/headed 실측과 구분한다. 합성 예제의 전체 개별매물 수는 152개이며 실제 NAS의 578개와 혼동하지 않는다. GitHub CI에는 기존 실제 NAS 이미지 통합 검사와 별도로 이 회귀 검사를 연결한다.
