# 2.5.3 — 업데이트 후 최초 전체 수집

새 코드로 컨테이너가 시작되고 브라우저가 준비되면 전체 수집을 한 번 자동 실행한다. 원격지에서 이미지 재빌드·컨테이너 재생성만 할 수 있을 때도 웹 화면의 버튼을 누를 필요가 없다. 이미지 빌드 중에 수집하는 방식은 아니다.

## 동작

- 기본 활성화다. ‘예약 수집 켜기’가 꺼져 있어도 최초 실행한다.
- 기존에 저장된 단지 주소·GitHub 설정을 사용한다. 새 설치는 기본 단지 140635를 사용한다.
- 표본검사 → 전체 수집 → 수량·가격·매물번호 검증 → NAS JSON 저장 순서를 유지한다.
- 성공하면 기존 ‘전체 수집 성공 후 자동 업로드’ 설정에 따라 GitHub로 전송한다. 토큰이 없거나 자동 업로드가 꺼져 있으면 NAS 저장까지만 수행한다. 토큰이나 업로드 설정을 임의로 생성·변경하지 않는다.
- 첫 실행 여부는 버전 문구가 아닌 런타임 소스 fingerprint로 구분한다. 같은 코드로 단순 재시작·재빌드해도 반복하지 않는다. 코드가 바뀌면 새로 한 번 실행한다.
- `/config/startup-collections.json`에 실행 시도 기록을 먼저 저장한다. 실패·중단 후 재시작에서도 같은 코드를 자동 재시도하지 않는다. 최초 1회는 성공 보장이 아닌 실행 시도다.
- 브라우저 준비 전 또는 수집/업로드 진행 중에는 기다린다. 이미 도래한 예약과 겹치면 최초 실행이 해당 예약도 처리하므로 곧바로 중복 실행하지 않는다. 미래 예약 시각은 유지한다.
- 새 실행의 화면에는 ‘업데이트 후 최초 실행’이 표시된다. 기존 실행 방식 기록은 변경하지 않는다.
- 테스트 환경 등에서만 필요하다면 환경변수 `WHOGA_STARTUP_COLLECT=0`으로 최초 실행을 끌 수 있다. 기본 Compose에는 끄는 설정이 없다. GitHub CI의 합성 화면 검사에서는 이를 꺼 실제 사이트 자동 접근을 방지한다.

## 원격 업데이트

1. ZIP의 `nas/`, `experiments/`를 기존 WhoGa 경로에 덮어쓴다.
2. 기존 프로젝트 이름과 `.env`, 설정·결과 볼륨을 유지한다. 기존 방식에 맞는 Compose로 **재빌드 후 컨테이너를 재생성·시작**한다. 빌드만 완료하고 기존 컨테이너를 계속 실행하면 새 코드가 적용되지 않는다.
3. 브라우저 준비 후 스케줄러의 다음 확인(약 5초 이내)에서 최초 전체 수집을 시작한다. 웹 로그인이나 수동 클릭은 필요하지 않다.
4. NAS 결과는 기존 `/output/jobs/<jobId>/runs/<runId>/full.json`에 저장된다. GitHub 자동 전송 설정이 갖춰져 있다면 기존 대상 브랜치 `nas-imports/<단지번호>/<runId>.json`에서 확인한다.

```sh
# 설치 경로에서 기존 설치 방식에 해당하는 명령 하나만 사용
cd /volume2/docker/whoga/nas
sudo docker compose -f compose.yaml up -d --build
# 폴더 연결 방식이었다면 위 명령 대신:
# sudo docker compose -f compose.bind.yaml up -d --build
```

기존 볼륨을 삭제하거나 `down -v`를 실행하지 않는다. 설정 볼륨을 삭제하면 최초 실행 이력과 기존 인증·예약 설정도 사라진다.

## 검증

단위 검사 48개와 Chromium 화면 검사 5개 통과. 신규 검사는 예약 비활성 상태의 최초 실행, 브라우저 준비 대기, 실행 중 지연, 재시작·실패 후 중복 방지, 새 fingerprint 실행, 과거 fingerprint 복귀 시 중복 방지, 도래한 예약 통합, 미래 예약·업로드 설정 유지, 기록 저장 실패 시 실행 중단을 확인한다. 실제 NAS 배포 후 최초 수집과 GitHub 전달은 별도로 확인해야 한다.
